## Open findings that change development decisions

1. **Android v3 secondary send mismatch (source-confirmed):** `RadioEndpointKoinModule` binds
   `SecondaryGatewayRepository`; both its durable send methods throw. The production conversation/source
   coordinator injects that same scoped repository into `MeshtasticEndpointGatewaySource`, which can
   advertise READY native/overlay sending and delegates sends to those methods. The receiver returns
   `queue_failed`. Preserve v1/v2 isolation when correcting v3; do not simply expose the root repository
   to secondary endpoints. Current fake facade/token tests and the production graph-resolution test do
   not prove successful production secondary dispatch.
2. **Live history reset (source-confirmed):** `PacketRepositoryImpl.getGatewayHistoryState()` captures
   the epoch once per database subscription, while whole-history clear rotates persisted metadata.
   An existing subscriber can publish sequence zero with its old epoch until resubscription. Do not
   claim live reset/cursor correctness; synchronous fresh reads are a separate path.
3. **iOS QR callback ownership (review candidate, not device-reproduced):** Swift `didAdd` does not check
   `activeScanner === dataScanner`, whereas the unavailable callback does. Completion uses the current
   scanner/request ID. Review/test a late retired-scanner callback before claiming all stale native
   callbacks are rejected. This is not evidence of an observed wrong-channel apply.
4. **Windows first pairing:** Retained July 23 diagnosis records failed pairing/no PIN dialog. The
   PowerShell/WinRT helper still uses basic `PairAsync`; JVM fakes and macOS compilation do not establish
   a successful Windows pairing ceremony. Reproduce on Windows before claiming the client is fully
   independently usable with an unpaired radio.
5. **Validation inventory:** CI's explicit test shards omit `core:gateway`, `core:meshcore`,
   `core:radio-fleet`, `feature:meshcore`, and `ios:runtime`. Root `kmpSmokeCompile` uses a handwritten
   module list missing `core:radio-fleet`; dependency compilation can still cover it indirectly.
   Kotlin/Native test executable link **and execution** are disabled by convention. None of these
   mechanisms should be described as complete automatic three-platform test discovery.
6. **Static gate:** The September 5 1,946-task replay passed formatting, Debug builds/lints, tests and KMP compilation,
   but exits 1 for eight Detekt findings, not the previously reported six:
   BLE 3, domain 1, model 1, network 1, plus `core:ui` 2 `CompositionLocalAllowlist` findings in
   `LocalBarcodeScannerProvider.kt`. Record failures accurately; do not suppress them or claim a green
   root gate because the other tasks pass. Exact results are in the audit report.

Preserve the Android green brand and deployed Android IPC, preserve the Windows blue brand/startup/packaging behavior, and preserve the iOS isolated-endpoint/primary-only Apple Gateway boundary. A host-specific change must not silently alter another track.
- **Project Namespace:** New project-owned code must use `com.ntsocial.meshlink.*`. Do not introduce new `org.meshtastic.*` or `com.geeksville.mesh` project packages.
- **Protocol Boundary:** Keep generated upstream Meshtastic protobufs under `org.meshtastic.proto`. Do not edit `core/proto` unless the user explicitly requests upstream protocol/submodule work.
- **Semantic Meshtastic Names:** Existing identifiers such as `MeshtasticNavDisplay`, `MeshtasticNavigationSuite`, `MeshtasticBleConstants`, and `MeshtasticDatabase` may remain when they describe upstream protocol, device, database, or shell semantics. Do not perform cosmetic class renames without a scoped migration plan.
- **Android Gateway Boundary (v1/v2 compatibility + additive v3 fleet surface):** New Android NTsocial integrations must use the protected Gateway IPC. Keep every v1 path, column, command, and value immutable. `NtsocialGatewayService`/AIDL remains a deprecated compatibility adapter only; do not add features that bind it or directly bind `IMeshService`. New outbound traffic uses `PRIVATE_APP / port 256`; legacy `497` is receive-only compatibility. These Android ContentProvider/broadcast/AIDL mechanisms are neither a Windows nor an iOS IPC design.
- **Windows Integration Boundary (not implemented):** `NTsocial MeshLink` Windows is currently an independent Meshtastic desktop client intended to serve the separate `NTsocial_Windows` project in a future phase. Define and review an explicit Windows IPC/protocol, authentication, lifecycle, versioning, and threat model before integration work. Do not silently reuse Android IPC, expose internal database/service objects, import proprietary parent-App business logic, or describe branding/packaging as functional `NTsocial_Windows` interoperability.
- **iOS Apple Gateway Boundary (implemented; signed Debug READY evidence retained):** The iOS parent and companion remain separate Apps. The parent never links the GPL MeshLink KMP/radio implementation or opens a Meshtastic transport. Cross-App exchange uses schema-v1 `gateway-v1.sqlite` in App Group `group.com.ntsocial.gateway`, a 32-byte HMAC key in shared Keychain access-group suffix `com.ntsocial.meshlink.gateway`, payload-free Darwin hints, and `ntsocial-meshlink://process` for foreground handoff. MeshLink's Room database, authoritative in-memory routes, and private durable ledger stay outside the App Group; the parent canonical social store stays parent-private. Only the active legacy-primary iOS endpoint may publish Apple Gateway routes. It renews READY foreground projections at half the route TTL; inactive or non-ready state stops renewal, and source/generation/capability validation remains mandatory at every send. Source plist/entitlement declarations are not signed provisioning proof.
- **iOS Radio and Background Boundary:** Kable/CoreBluetooth is the only Apple Meshtastic BLE owner; do not add a parallel Swift radio stack. `ios/runtime` reuses `SharedRadioInterfaceService`, `DirectRadioControllerImpl`, Room, repositories, and `MeshServiceOrchestrator`. Transport replacement/retargeting within an endpoint synchronously rotates an atomic session epoch and revoke the retired transport callback generation before asynchronous teardown; only the same active session may mark configuration complete. The switch path quiesces radio-owned ingress and registered child work, awaits the retired generation's outbound queue/status/log work, switches the active per-radio database, hydrates that database's node cache, and only then resumes/connects. Gateway route issue/admission and inbound projection use the exact private session/database/readback identity, while selection/connect/disconnect/forget plus admission share `ChannelOperationLock`. Selecting a fleet UI tab only changes the selected endpoint; it does not replace other endpoints' transports/databases or transfer primary Apple Gateway ownership. CoreBluetooth restoration, Darwin hints, and deep links are best-effort recovery mechanisms, never an always-running service, terminated-App launch guarantee, or remote-delivery proof.
- **iOS Channel Mutation and Dispatch Boundary:** Manual/QR apply, protected reconcile, and built-in provision share `validate/ensure → invalidate ingress → exact-session mutation → correlated fresh readback → activate`. Full mutation serialization must not hold the short `ChannelOperationLock` while the readback producer commits. Exact readback reuses firmware `69420`; a host-exclusive session/token owner may start only after prior FULL Stage 2, completes on a dedicated host flow, and rejects stale/parallel FULL, old-session, and generic-generation events. If its admitted caller times out/cancels and firmware never returns, that epoch remains fail closed until reconnect/new epoch (known liveness P2). Gateway Room rows retain accepted source identity; actual drain revalidates active session/ingress plus slot-derived PSK/LoRa identity and holds the operation boundary through exact-session queue admission and matching QueueStatus. A changed slot identity is terminally fail closed, never routed by numeric slot alone.
- **iOS Gateway Contract:** The exact parent caller is `com.ntsocial.ios`. Routes are 32 CSPRNG bytes encoded Base64URL, expire after 120 seconds, and are bound in process memory to caller, source channel, captured slot, and opaque generation; process start or channel/routing-context inequality rotates generation and invalidates them. Client IDs are exactly 32 hexadecimal characters and canonicalized uppercase. HMAC uses versioned length-delimited canonical bytes and SHA-256 with expiry, key-version, nonce-replay, and constant-time checks. The private ledger retains at most 256 insertion-ordered records per caller without TTL. `ACCEPTED_LOCAL` is appended only after durable Room/retry admission and accepted-ledger commit and never means firmware airtime, RF delivery, or remote receipt. Before resolving a process-local route, an authenticated exact request may replay an already-accepted private-ledger record after restart; only its existing packet ID is published, no second radio admission occurs, and different content for that client ID remains `IDEMPOTENCY_CONFLICT`.
- **iOS Gateway Data Surface:** App Group v1 exposes only status/caller/channel projections, immutable command inbox plus separate reclaimable claims, append-only command results, bounded complete-`NM` overlay ingress (maximum 128 retained rows), `overlay_epoch_state`, paged stable-only native broadcast-text insertion changes (default 100, maximum 200), consumer cursors, and nonce reservations. `overlay_epoch_state(history_epoch, high_water)` is additive within schema/user-version 1, is backfilled from retained rows when absent, advances atomically with overlay append, survives retention eviction, and is cleared only by an explicit reset. Port 256 is outbound; port 497 is receive-only compatibility. Native changes require identities captured at private-Room insertion and never derive nullable legacy identity from a current slot. Never add PSKs, precise position, raw radio config/protobuf, private history, account secrets, or HMAC key bytes.
- **iOS Parent Adapter Contract (external parent source; bounded signed Debug evidence):** A first-send `pendingLocalAcceptance` is durably recorded immediately as exact message/attempt/transport `.queued` plus `.admission`; it is never promoted to accepted or rejected until a matching terminal result, and one later same-attempt `ACCEPTED_LOCAL` performs one acknowledgement/cursor advance. Parent-private restart correlation retains the final social-header message ID, attempt, multipart kind/index/count, transfer ID, and logical channel; it must not reconstruct a final ID from the outer chunk header or hard-coded direct-message values. The mailbox/catalog may retain slot-indexed duplicate source identities for outbound routes, while canonical/history projection collapses equal stable identities deterministically—PRIMARY first, then the lowest slot—and rejects conflicting security semantics. Same-epoch retained backlog uses the historical resolver. An irrecoverable retention gap, malformed envelope, or lost/expired multipart transfer is skipped only after a durable gap/quarantine/abandoned-transfer terminal record; only then may the cursor advance to `firstRetained - 1` or beyond deterministic poison. Transient store/projection failure never advances the cursor, and rows already evicted are not claimed recoverable. These parent-side contracts are retained integration requirements; consult the separately authorized parent source before changing them. September 3 memory records manual binding and route-expiry recovery with local acceptance, not complete parent-to-parent remote delivery.

- **Gateway Cursor Domains:** `history_epoch` is a durable random value in the active per-radio Room database. Initial creation and whole-history clear persist it transactionally; switching databases exposes the target database's stored epoch rather than rotating on every switch. `not-ready` is transient and must not be persisted or treated as a reset. The current active publisher has a known defect: `getGatewayHistoryState()` captures the epoch once per subscription, so a whole-history clear can publish sequence zero with the old epoch until the history flow is resubscribed, for example by an active-database switch or process restart. - **Native Text Insertion Cursor:** `/v2/message-changes` is an insertion cursor, not a general change feed. It includes only unfiltered broadcast `TEXT_MESSAGE_APP` rows inserted by live ingress, Store & Forward router-text broadcast, MeshLink's own native send, or accepted Gateway `SEND_CHANNEL_TEXT`, with both stable identity columns captured at insertion. Gateway-originated rows may additionally expose nullable `origin_client_message_id` for reliable parent own-echo correlation; it is local metadata and never enters the Meshtastic packet/protobuf. DMs, reactions, filtered rows, state/control traffic, port-256 NTsocial overlays, and upgraded nullable legacy rows are excluded; updates and deletes create neither a new sequence nor a tombstone. A nullable legacy row must never be recomputed from current slot/config state because slot reuse could assign channel A's message to channel B. `change_seq` is the monotonically increasing Room packet `uuid` within one database, not a message ID, timestamp, delivery state, or cross-database order. The v2 status high-water uses the same stable-only predicate, so it never advances to an unexportable nullable row. The default page is `after=0&limit=100`, the maximum limit is 200, and negative/repeated/unknown parameters are rejected. Consumers must pair the cursor with a real epoch, restart at zero on epoch change, advance to the maximum returned sequence, and retry without mutating durable cursor state while status is `not-ready`.
- **Room 43 Gateway Schema:** Auto-migration 41-to-42 adds nullable `gateway_source_channel_id` and `gateway_source_message_id` packet columns, non-unique lookup indexes, and the `gateway_metadata` table. Auto-migration 42-to-43 adds only nullable `origin_client_message_id`; it does not backfill or alter serialized packet/protobuf data. Rows that remain without captured stable identity stay available only to MeshLink's internal/local compatibility views and are not Gateway v2 history. Duplicate Room rows may share a stable source-message ID, so clients dedupe by exported identity rather than assuming database-row uniqueness. Generated schemas/unit gates are not retained proof of real on-device migrations.
- **Gateway Commands:** A parent App obtains an in-memory, request-bound, single-use capability with a 30-second TTL from the Provider, then sends an explicit `com.ntsocial.meshlink.gateway.COMMAND`. Android 8-13 relies on the consumed capability; Android 14+ also verifies the broadcast sender UID, package, and certificate. Never trust caller-supplied package names or ports, and never use implicit broadcasts.
- **Gateway Routes and Idempotency:** Each v2 catalog query issues a random 32-byte, in-memory route token with a 120-second TTL. It is reusable until expiry but bound to the exact verified caller UID/package, source-channel ID, captured slot, and current radio generation; process restart loses it. A routed command does not accept or trust a caller channel index. `client_message_id` accepts exactly 32 hexadecimal characters and is canonicalized to uppercase. The durable ledger is capped at 256 insertion-ordered records, keyed by caller package plus canonical ID for legacy commands, and by caller package plus endpoint ID plus canonical ID for v3, and has no TTL; reuse with a different request fingerprint is an idempotency conflict. v3 tokens also bind the exact endpoint, endpoint generation, and fleet generation; retain old two-part ledger keys when loading legacy entries. Fleet generation derives from endpoint IDs, endpoint/catalog generations, and history epochs; message sequence/readiness is excluded. Keep this distinct from the legacy opaque `radio_generation` contract.
- **Routed Command Commit Order:** Both routed v2 sends first durably commit the PENDING ledger reservation, then insert or exact-content-check the deterministic packet ID in Room, await unique WorkManager `REPLACE` admission, commit ACCEPTED, and only then emit `COMMAND_ACCEPTED`. If the final ACCEPTED ledger commit fails after Room/WorkManager success, `queue_failed` does not prove the packet was unscheduled; retry the same client ID. A crash between local admission and durable acceptance can still cause a physical RF duplicate, so this is restart-stable local idempotency, not exactly-once radio delivery.
- **Gateway Events:** `com.ntsocial.meshlink.gateway.EVENT` is explicitly package-scoped and metadata-only. It may carry event type, URI, request ID, packet ID, or rejection reason; it must never carry message bytes, destinations, precise location, PSKs, tokens, or radio configuration. A client re-queries the Provider after an event.
- **Trusted Pairing:** The in-process UID/package/certificate verifier is authoritative. Both Debug and Release MeshLink builds accept `com.ntsocial.android` with the approved release signer and accept `com.ntsocial.android.debug` with either the stable team-debug signer or retained development-debug signer `B578...3FF8`; host and caller build types do not need to match. A debuggable MeshLink host additionally accepts only the exact debug parent when both Apps have identical, nonempty complete current-signer sets. Empty identities, unknown signers, partial multi-signer overlap, and arbitrary package names fail closed; a nondebuggable host has no unpinned fallback. Ordinary permission grant is not sufficient by itself. Private keys remain outside the repository. A production package or signer change requires a synchronized update to verifier rules, known-signer resources, NTsocial package visibility/trust, and both build configurations; never broaden this to arbitrary installed Apps.
- **Outbound Transport Contract:** v1 external commands accept only a validated complete `NM` envelope, unchanged, on the currently ready canonical default RF index; acceptance is the synchronous `CommandSender` return. v2 `SEND_NTSOCIAL_ENVELOPE_TO_ROUTE` accepts the same envelope only with a current caller-bound `source_channel_id`/`route_token` pair and uses the slot captured by that route. Both overlay paths use `PRIVATE_APP / port 256` and cap the complete envelope at 180 bytes. Additive v2 `SEND_CHANNEL_TEXT` uses the same capability, caller-bound route, radio generation, client-message ledger, Room, and WorkManager commit order, but accepts only nonblank text at most 180 UTF-8 bytes and constructs an unfiltered broadcast `TEXT_MESSAGE_APP` row for MeshLink's normal channel UI. Its dynamic route revalidation, existing-row check, insertion, and queue admission are serialized by the repository's native-text owner so concurrent retries cannot create duplicate chat rows. It never accepts a destination, caller slot, port, packet ID, or encoded packet. Every accepted result is local admission only, never firmware airtime or remote receipt. `497` is never an outbound command port.
- **Gateway Identity:** Every encrypted channel derives `source_channel_id` only from a domain-separated SHA-256 digest of the resolved `ModelChannel.psk`; configured name, slot, role, numeric channel ID, and install state are excluded. Meshtastic shorthand PSKs 1 through 10 are resolved before hashing, so shorthand and their full-key forms converge; `security_class` is likewise based on the resolved PSK (`CLEAR`, the ten `WELL_KNOWN` keys, or `CUSTOM`). CLEAR compatibility is byte-for-byte retained: a nonzero `ChannelSettings.id` uses the existing unsigned numeric-ID domain, while a zero-ID CLEAR channel uses the existing canonical resolved-name plus empty-key domain. Existing rows that already captured an older source ID retain that exact partition; do not alias or rewrite them. `source_message_id` is the uppercase first 32 hex characters of a domain-separated SHA-256 over stable channel ID, normalized sender node ID, unsigned packet ID, port, and payload hash; use it for import dedupe even when duplicate Room rows exist. Never export `!local` as a durable author: normalize local outgoing native text to the stable own-node ID before identity capture, and fail closed until that ID is known.
- **Gateway Identity-Key Storage:** The obsolete install-local legacy HMAC provider and its Android/Desktop dependency-injection seams are removed. An old private preference left by an upgraded install is inert and is neither read nor exported. Desktop still compiles the shared PSK-derived identity/capture path but does not expose the Android Provider contract or a Windows Gateway IPC.
- **Cache and Acceptance Semantics:** The bridge cache is transient, in-memory, and bounded to 128 envelopes; NTsocial remains the social UX and canonical-history owner. For routed Android v2/v3 commands, `COMMAND_ACCEPTED` means Room and platform retry work were committed locally; it does not mean the firmware accepted RF airtime or any remote radio/NTsocial peer received it. Overlay sends do not appear as ordinary Meshtastic native-text messages.
- **Node Policy:** `rebroadcast_mode = ALL` is an NTsocial Node Policy applied with clear user consent and verification, not a silent forced configuration.
- **Channel Model:** `source_channel_id` is the durable radio-side identity and must be treated as opaque. Slot/index is only a mutable locator. MeshLink owns neither a parent NTsocial logical `channelId`, group membership, nor logical binding; many parent logical channels may intentionally route through one source channel.
- **Parent Channel Policy:** Gateway v1 validates only the canonical ready default index. Gateway v2 ignores any caller notion of channel index and resolves any current configured catalog slot exclusively from the caller/source/generation-bound route token. The parent may automatically create a dedicated logical projection for every catalog row; that must not erase the separate opt-in workflow that manually binds an ordinary parent channel to a source channel. v3 additionally requires the endpoint-bound route; neither a UI endpoint selection nor a copied slot may substitute for that identity.
- **Built-In NTsocial Channel:** NTsocial MeshLink bundles the canonical public NTsocial Meshtastic channel and automatically ensures it is registered after node-database readiness. Provisioning may rewrite only a slot whose name equals the canonical NTsocial name case-insensitively or whose PSK exactly matches, including primary; otherwise it appends at the current settings-list size when below the radio maximum (primary only for an empty list, secondary thereafter). `NO_SPACE` performs no channel write and must not mutate an unrelated slot. Applying default LoRa config and then writing the channel are sequential radio commands, not a transaction: if the second command fails, an already accepted LoRa-config change may remain. This automatic registration does not require a user confirmation dialog.
- **LoRa Config Preservation:** Built-in NTsocial channel provisioning may apply the QR LoRa/RF config only when the radio is effectively unconfigured, such as missing LoRa config or `region == UNSET`; never overwrite an already configured region/frequency/preset.
- **LoRa Payload Policy:** Do not route image bytes, voice bytes, or PTT media over LoRa. LoRa roadmap payloads are text, state/control, profile/channel snapshots, roster/probe data, chunks, and receipts.
- **Open-Source Boundary:** This GPL fork must not embed closed NTsocial App business logic, private assets, secrets, or production credentials. Protocol/schema/IPC work intended for this Gateway should remain open.
- **Restricted Data Surface:** Raw envelope bytes are available only to a verified Provider client. Node/channel snapshots must not grow to expose positions, PSKs, RF configuration, notes, or raw protobufs, and none of those values may appear in events or logs.
- **Cloud Runtime Boundary:** Neither Android flavor may package Google Cloud, Maps, Google Play services, Firebase, Crashlytics, Datadog, ML Kit, Advertising ID/AdServices, Install Referrer, or equivalent telemetry/runtime configuration. The `google` flavor label identifies the Play publication path and never authorizes a Google service dependency. It still uses the non-Google Meshtastic project `ApiServiceImpl` for device/firmware information, while `fdroid` intentionally falls back to bundled JSON; do not assume the flavors are otherwise behaviorally identical. QR/barcode decoding is local ZXing; rendered maps are intentionally absent. Android platform location and Meshtastic radio/MQTT location controls remain because they are independent app capabilities, not Google cloud services.
- **Analytics Compatibility Seam:** `PlatformAnalytics` and existing `track()` call sites remain only to preserve upstream-compatible manager contracts. Every Android flavor must resolve them to `NoopPlatformAnalytics`, which never records, stores, or transmits events. Do not add a network-backed implementation or treat these call sites as evidence that telemetry still exists.
- **Play Data Disclosure Boundary:** No publisher analytics/crash backend does not mean that Play Data safety can claim "no collection." Mesh messages, names/IDs, optional phone location, and user-configured transports can leave the Android device. Shared-PSK channels, Ham mode, or unencrypted user-configured endpoints also prevent a blanket claim that every collected data type is encrypted in transit. Keep the Data safety form, privacy policy, prominent disclosures, and final network behavior aligned; use the conservative current draft until artifact-level testing proves a documented exception.
- **Location FGS Release Boundary:** `MeshService` now adds the location foreground-service type only while the existing per-node phone-location opt-in is enabled, Fine or Coarse permission is granted, and system location is active; opt-out drops the type and stops the listener, and the App does not request background location. Before Production, validate this path on Android 11-17/API 30-37 across permission revocation/regrant, system-location changes, foreground/background, reconnect, process restart, and target OEM behavior, then keep Play disclosure and minimum-scope UI aligned. Do not broaden the permission or imply second-radio delivery without hardware evidence.
- **UGC Release Boundary:** Before Production, users must accept the applicable terms before first sending UGC, have an in-app content/user reporting path, and have an effective block/ignore path for one-to-one interaction. Public Markdown pages, GitHub issues, or a support email are backups, not substitutes. Do not publish the draft Terms/Community pages as final until these flows exist and have been tested.
- **Store Metadata Boundary:** `docs/google-play/` is authoritative for the cloud-free first release. Do not upload legacy Fastlane copy/screenshots that still show maps, analytics, or official-Meshtastic claims. Policy Markdown files are drafts until their warning blocks are removed, hosted on stable public HTTPS pages, and wired back into the final App artifact.
</architecture_boundaries>

<rules>
- **Token Hygiene:** Never read binary files such as PNG, MP3, APK, or large non-code resources unless essential. Use file paths to reason about assets.
- **Context Discipline:** Limit context to relevant modules. Do not vacuum the entire codebase for localized fixes.
- **No Lazy Coding:** Do not use placeholders such as `// ... existing code ...`. Provide complete, valid code.
- **No Framework Bleed:** Never import `java.*` or `android.*` in `commonMain`. Use KMP equivalents such as Okio, `Mutex`, and atomicfu.
- **CMP Over Android:** Use Compose Multiplatform constraints. Pre-format floats with `NumberFormatter.format()`. Use `MeshtasticNavDisplay` and `NavigationBackHandler`.
- **Zero Lint Tolerance:** Do not add or suppress new findings; `spotlessCheck` and every
  changed-module Detekt task must pass, and full root `detekt` remains the authoritative release gate.
  The September 5 source baseline is not full-root green: eight findings in `core/ble` (three),
  `core/domain` (one), `core/model` (one), `core/network` (one), and `core/ui` (two).
  Record that blocker honestly on unrelated work, and fix it rather than suppress it when those
  files or the release gate are in scope.
- **Verify Before Push:** Treat any push as verify-then-push. Check GitHub Actions state before pushing when GitHub context is relevant.
- **Never Touch Protos or Secrets:** `core/proto` is an upstream submodule. Secrets are git-ignored and must not be logged, committed, or exposed.
- **Privacy First:** Never log or expose PII, precise location, private messages, cryptographic keys, tokens, or pairing credentials.
- **Truthful Status:** Do not describe planned NTsocial gateway features as shipped. Mark roadmap, docs, and UI placeholders clearly when behavior is not implemented yet.
- **Attribution Integrity:** Do not remove upstream copyright, license, warranty, or third-party notice text. Do not hand-edit a different Kotlin/KTS/XML header; update the synchronized Spotless/Detekt templates and preserve excluded wrapper, submodule, generated, and third-party headers.
</rules>
